● Leçon 7 — Dépannage : trouver pourquoi ça ne marche pas

  Le programme initial (leçons 1 à 6) est terminé. Parmi les bonus proposés, je
  commence par le dépannage : tu as déjà rencontré un Access denied, et c'est la
  compétence qui sert tous les jours.

  La méthode tient en 4 questions, toujours dans le même ordre.

  1. Le conteneur tourne-t-il ?

  docker compose ps -a      # -a : montre aussi les conteneurs arrêtés

  ┌───────────────────┬────────────────────────────────────────┐
  │      STATUS       │             Signification              │
  ├───────────────────┼────────────────────────────────────────┤
  │ Up / Up (healthy) │ il tourne                              │
  ├───────────────────┼────────────────────────────────────────┤
  │ Up (unhealthy)    │ il tourne, mais son healthcheck échoue │
  ├───────────────────┼────────────────────────────────────────┤
  │ Exited (0)        │ terminé normalement                    │
  ├───────────────────┼────────────────────────────────────────┤
  │ Exited (1)        │ planté sur une erreur : lire les logs  │
  ├───────────────────┼────────────────────────────────────────┤
  │ Exited (127)      │ commande introuvable                   │
  ├───────────────────┼────────────────────────────────────────┤
  │ Exited (137)      │ tué (souvent par manque de mémoire)    │
  ├───────────────────┼────────────────────────────────────────┤
  │ Restarting        │ plante en boucle                       │
  └───────────────────┴────────────────────────────────────────┘

  2. Que dit-il ?

  docker compose logs --tail 50 app   # les 50 dernières lignes de app
  docker compose logs -f              # tous les services, en direct

  3. Qu'y a-t-il dedans ?

  docker compose exec app bash        # entrer dans un conteneur qui tourne
  docker compose exec app env         # ses variables d'environnement
  docker compose run --rm app bash    # s'il plante au démarrage : en lancer un 
  neuf avec bash à la place

  4. Quelle configuration est réellement appliquée ?

  docker compose config     # le compose.yaml final, avec les variables du .env 
  remplacées

  Le piège classique

  docker compose restart redémarre les mêmes conteneurs avec l'ancienne
  configuration. Après une modification du compose.yaml ou du .env, c'est docker
  compose up -d qu'il faut : il recrée ce qui a changé.

  Exercices (dans monapp/)

  Tu vas casser ton appli exprès, puis la réparer avec la méthode.

  1. Casser : dans compose.yaml, remplace DB_HOST: db par DB_HOST: base, puis
     lance docker compose restart. Recharge http://localhost:8090 : ça marche
     encore. Pourquoi ?
  2. Lance maintenant docker compose up -d et recharge la page : cette fois
     c'est cassé.
  3. Enquêter : applique les 4 questions.
     - docker compose ps -a : le conteneur app tourne-t-il ?
     - docker compose logs --tail 20 app : quel message d'erreur trouves-tu ?
     - docker compose exec app env | grep DB : que vaut DB_HOST ?
  4. Réparer : remets DB_HOST: db, puis docker compose up -d.
  5. Lance docker compose config et regarde ce qu'est devenu ${DB_PASSWORD}.
  6. Lance docker system df pour voir la place prise par Docker sur ton disque.

  Récap

  - L'ordre est toujours : état (ps -a), logs, intérieur (exec), configuration
    (config).
  - Un conteneur peut être Up alors que l'appli dedans est en erreur : ce sont
    les logs qui le disent.
  - restart ne relit pas le fichier, up -d oui.

  J'ai ajouté la leçon 7 à cours-docker.md (case à cocher quand tu auras fait
  les exercices).

  Question pour la suite : lance docker images monapp-app et regarde la colonne
  SIZE. Ton index.php pèse 488 octets : d'où vient tout le reste, et comment
  faire une image plus légère ?

● Leçon 8 — Taille des images et build multi-étapes

  Réponse à la question : ton image monapp-app pèse 738 Mo, et presque tout
  vient de l'image de base php:8.5-apache (Debian, Apache, PHP, outils de
  compilation). Tes propres couches pèsent environ 100 Ko. Tu le vois avec :

  docker history monapp-app

  Il y a trois leviers pour alléger une image.

  1. Une couche ne fait qu'ajouter

  Supprimer un fichier dans un RUN suivant ne libère rien : il reste dans la
  couche d'avant.

  # ❌ le cache apt reste dans la première couche
  RUN apt-get update && apt-get install -y git
  RUN rm -rf /var/lib/apt/lists/*

  # ✅ installé et nettoyé dans le même RUN
  RUN apt-get update && apt-get install -y git \
      && rm -rf /var/lib/apt/lists/*

  2. Une image de base plus légère

  Les variantes -alpine reposent sur Alpine Linux (4 Mo) au lieu de Debian. Tu
  en as déjà une : redis:8-alpine. Deux limites : il n'existe pas de
  php:apache-alpine, et Alpine utilise apk au lieu de apt-get.

  3. Le build multi-étapes : l'atelier et la vitrine

  Pour installer des dépendances PHP il faut Composer, git et unzip, mais
  l'appli n'en a plus besoin une fois lancée. On met donc plusieurs FROM dans le
  Dockerfile : seule la dernière étape devient l'image, les autres sont jetées
  après usage.

  # Étape 1 — l'atelier : Composer télécharge les dépendances
  FROM composer:2 AS vendor
  WORKDIR /app
  COPY composer.json .
  RUN composer install --no-dev --no-interaction

  # Étape 2 — la vitrine : l'image finale
  FROM php:8.5-apache
  WORKDIR /var/www/html
  COPY --from=vendor /app/vendor ./vendor
  COPY src/ .

  AS vendor donne un nom à l'étape, et COPY --from=vendor va y chercher
  uniquement le dossier vendor.

  Exercices

  Crée un nouveau dossier /var/www/docker/multietape/ avec trois fichiers.

  composer.json :
  {
      "require": {
          "nesbot/carbon": "^3.0"
      }
  }

  src/index.php :
  <?php
  require __DIR__ . '/vendor/autoload.php';

  use Carbon\Carbon;

  echo "<h1>Image multi-étapes</h1>";
  echo "<p>Nous sommes le " . Carbon::now()->locale('fr')->isoFormat('dddd D 
  MMMM YYYY') . "</p>";

  Dockerfile : celui ci-dessus.

  Puis :

  1. docker build -t multietape .
  2. docker run -d --rm --name multi -p 8091:80 multietape, puis ouvre
     http://localhost:8091 : la date s'affiche en français.
  3. docker exec multi composer --version : que répond-il, et pourquoi ?
  4. docker exec multi ls vendor : les dépendances sont pourtant bien là.
  5. docker history multietape : cherche la ligne COPY --from. Vois-tu une trace
     de composer install ?
  6. docker stop multi pour terminer.

  J'ai vérifié cet exemple sur ta machine : 746 Mo en multi-étapes contre 862 Mo
  en installant Composer, git et unzip dans l'image finale. L'image composer:2
  est donc déjà téléchargée chez toi, et j'ai supprimé mes images de test.

  Récap

  - Le poids d'une image vient surtout de son image de base : docker history le
    montre.
  - Installer et nettoyer se font dans le même RUN.
  - En multi-étapes, les outils de fabrication restent dans l'atelier et l'image
    finale ne contient que le résultat.
  - Les versions de PHP des deux étapes doivent être compatibles, sinon Composer
    refuse de démarrer l'appli.
