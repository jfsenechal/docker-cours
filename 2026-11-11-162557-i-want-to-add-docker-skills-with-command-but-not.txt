  Étape 0 : comprendre en 2 minutes

  Le problème que Docker résout : « ça marche sur ma machine, mais pas sur le
  serveur ». Les versions de PHP, MySQL ou des librairies ne sont jamais tout à
  fait les mêmes d'une machine à l'autre.

  La solution : on emballe l'application avec tout son environnement dans une
  boîte standard, comme un conteneur de bateau.

  Les 4 mots à retenir :

  ┌────────────┬──────────────────┬─────────────────────────────────────────┐
  │    Mot     │     Analogie     │                 En vrai                 │
  ├────────────┼──────────────────┼─────────────────────────────────────────┤
  │ Image      │ Une recette ou   │ Un modèle figé en lecture seule (ex. :  │
  │            │ un moule         │ php:8.3, mysql:8)                       │
  ├────────────┼──────────────────┼─────────────────────────────────────────┤
  │            │ Le gâteau sorti  │ Une image en train de tourner. On peut  │
  │ Conteneur  │ du moule         │ en lancer plusieurs à partir de la même │
  │            │                  │  image.                                 │
  ├────────────┼──────────────────┼─────────────────────────────────────────┤
  │ Dockerfile │ La recette       │ Le fichier texte qui décrit comment     │
  │            │ écrite           │ fabriquer ta propre image               │
  ├────────────┼──────────────────┼─────────────────────────────────────────┤
  │ Docker Hub │ Le supermarché   │ Le site (hub.docker.com) où l'on        │
  │            │ des recettes     │ télécharge les images officielles       │
  └────────────┴──────────────────┴─────────────────────────────────────────┘

  Le cycle de base :

  Dockerfile  --(docker build)-->  Image  --(docker run)-->  Conteneur
                                     ^
                      Docker Hub --(docker pull)

  Un conteneur n'est pas une machine virtuelle. Il partage le noyau Linux de ton
  PC, c'est pour ça qu'il démarre en une seconde et consomme peu.

● Leçon 3 : les ports

  ✅ Bonne réponse ! Pour être précis : nginx écoute bien sur le port 80, mais à
  l'intérieur du conteneur. Le conteneur a son propre réseau isolé, et ton PC
  ne sait pas qu'il doit lui transmettre ce qui arrive. Il faut publier le port.

  ---

  1. Le principe

   Navigateur                   Ton PC (hôte)                  Conteneur
  http://localhost:8080  ──►   port 8080   ──── -p ────►   port 80 (nginx)

  La syntaxe est toujours -p PORT_HÔTE:PORT_CONTENEUR.

  ▎ Moyen mnémotechnique : dehors : dedans.

  ---

  2. Exercice A : ton premier site accessible

  D'abord, supprime l'ancien monweb s'il existe encore :

  docker rm -f monweb      # -f = arrête puis supprime en une seule commande

  Puis :

  docker run -d --name monweb -p 8080:80 nginx

  Ouvre http://localhost:8080 dans ton navigateur : tu dois voir « Welcome to 
  nginx! » 🎉

  Vérifie aussi avec :

  docker ps            # colonne PORTS : 0.0.0.0:8080->80/tcp
  docker port monweb   # affiche les ports publiés
  docker logs monweb   # tu vois la requête de ton navigateur passer !

  ---

  3. Exercice B : plusieurs conteneurs, plusieurs ports

  Une même image peut tourner plusieurs fois, à condition d'utiliser un port 
  hôte différent pour chaque conteneur :

  docker run -d --name web2 -p 8081:80 nginx
  docker run -d --name web3 -p 8082:80 nginx

  → http://localhost:8081 et http://localhost:8082 fonctionnent aussi. Les trois
  écoutent sur le port 80 chez eux, sans conflit.

  Maintenant, provoque volontairement une erreur :

  docker run -d --name web4 -p 8080:80 nginx

  Tu obtiens port is already allocated : le port hôte 8080 est déjà pris par
  monweb. Côté hôte, un port ne peut servir qu'à un seul conteneur à la fois.

  Le conteneur web4 a quand même été créé, mais il n'a pas pu démarrer. Fais le
  ménage :

  docker rm -f web2 web3 web4

  ---

  4. Exercice C : modifier la page… et la perdre 😱

  On change la page d'accueil depuis l'intérieur du conteneur :

  docker exec monweb sh -c 'echo "<h1>Mon premier site Docker</h1>" > 
  /usr/share/nginx/html/index.html'

  Rafraîchis http://localhost:8080 : ta page s'affiche.

  Maintenant, on supprime le conteneur et on le recrée :

  docker rm -f monweb
  docker run -d --name monweb -p 8080:80 nginx

  Rafraîchis : ta page a disparu, tu retrouves « Welcome to nginx! ».

  ---

  Récap

  - -p 8080:80 → hôte:conteneur
  - Un port hôte ne peut être utilisé que par un seul conteneur à la fois.
  - docker port <nom> affiche les ports publiés.
  - docker rm -f arrête et supprime en une seule commande.
  - Les modifications faites dans un conteneur disparaissent quand on le
    supprime.

● Leçon 4 : les volumes (pour garder ton job 😄)

  ✅ Exactement. Un conteneur doit être jetable : on le supprime et on le recrée
  sans regret. Les données, elles, doivent vivre à l'extérieur du conteneur.
  C'est le rôle des volumes.

  ---

  1. Les deux façons de stocker des données

                         Ton PC (hôte)                     Conteneur
   Bind mount :     ~/docker-cours/site/   ◄──────►   /usr/share/nginx/html
   Volume nommé :   [géré par Docker]      ◄──────►   /var/lib/mysql

  Type: Bind mount
  Syntaxe: -v /chemin/sur/pc:/chemin/conteneur
  Quand l'utiliser: Ton code pendant le développement : tu modifies un fichier
    sur ton PC et le conteneur voit le changement immédiatement
  ────────────────────────────────────────
  Type: Volume nommé
  Syntaxe: -v nom_volume:/chemin/conteneur
  Quand l'utiliser: Les données (bases de données…). Docker les range lui-même,
    et tu n'as pas à t'en occuper.

  Pour les deux, la logique est la même que pour les ports : dehors : dedans.

  ---

  2. Exercice A : bind mount, ton site sur ton PC

  On crée un dossier de travail avec une page :

  mkdir -p ~/docker-cours/site
  cd ~/docker-cours
  echo "<h1>Mon site, stocké sur MON PC</h1>" > site/index.html

  On relance nginx en montant ce dossier à la place du dossier web du conteneur
  :

  docker rm -f monweb
  docker run -d --name monweb -p 8080:80 -v $(pwd)/site:/usr/share/nginx/html:ro
  nginx

  - $(pwd) est remplacé par le dossier courant. Un bind mount exige un chemin 
    absolu.
  - :ro signifie read-only : le conteneur peut lire les fichiers, mais pas les
    modifier. C'est plus sûr.

  → http://localhost:8080 affiche ta page.

  Maintenant, modifie le fichier sur ton PC avec l'éditeur de ton choix, ou avec
  :

  echo "<h1>Modifié en direct !</h1>" > site/index.html

  Rafraîchis le navigateur : le changement apparaît immédiatement, sans
  redémarrer le conteneur. Et si tu fais docker rm -f monweb puis que tu
  relances, ta page est toujours là, puisqu'elle est sur ton PC.

  ---

  3. Exercice B : volume nommé, une vraie base MySQL

  Nouvelle option : -e, qui passe une variable d'environnement au conteneur.
  L'image MySQL l'exige pour définir le mot de passe root.

  docker volume create mesdonnees

  docker run -d --name madb \
    -e MYSQL_ROOT_PASSWORD=secret \
    -v mesdonnees:/var/lib/mysql \
    mysql:8

  Attends environ 20 secondes que MySQL démarre (docker logs -f madb jusqu'à
  voir ready for connections, puis Ctrl+C). Ensuite, crée des données
  importantes :

  docker exec -it madb mysql -uroot -psecret

  CREATE DATABASE boulot;
  USE boulot;
  CREATE TABLE clients (nom VARCHAR(50));
  INSERT INTO clients VALUES ('Client très important');
  SELECT * FROM clients;
  exit

  Le test qui sauve ton job : on détruit le conteneur…

  docker rm -f madb

  …puis on en recrée un tout neuf, branché sur le même volume :

  docker run -d --name madb -e MYSQL_ROOT_PASSWORD=secret -v
  mesdonnees:/var/lib/mysql mysql:8

  Attends quelques secondes, puis :

  docker exec -it madb mysql -uroot -psecret -e "SELECT * FROM boulot.clients;"

  → « Client très important » est toujours là. Tu es sauvé·e. 🎉

  ---

  4. Gérer les volumes

  docker volume ls                    # liste les volumes
  docker volume inspect mesdonnees    # détails, dont l'emplacement réel sur le 
  disque
  docker volume rm mesdonnees         # ⚠️ SUPPRIME DÉFINITIVEMENT les données

  À retenir : docker rm sur un conteneur ne supprime pas ses volumes nommés,
  c'est voulu. En revanche, docker volume rm et docker volume prune effacent les
  données pour de bon. En production, ce sont ces commandes qui font virer les
  gens, alors relis-toi toujours avant de les lancer.

  ---

  Récap

  -v /chemin/absolu/pc:/chemin/conteneur     → bind mount (ton code)
  -v nom_volume:/chemin/conteneur            → volume nommé (tes données)
  :ro                                        → lecture seule
  -e VARIABLE=valeur                         → configurer le conteneur
  docker volume ls / inspect / rm            → gérer les volumes

  La règle d'or : le conteneur est jetable, les données sont dans un volume.

● Leçon 5 : ton premier Dockerfile

  ✅ Exactement. Un Dockerfile, c'est la recette de ton image : on part d'une
  image existante, on ajoute ce dont on a besoin, et on obtient ta propre image.

  ---

  1. Les instructions de base

  ┌─────────────┬──────────────────────────────┬────────────────────────────┐
  │ Instruction │             Rôle             │          Exemple           │
  ├─────────────┼──────────────────────────────┼────────────────────────────┤
  │ FROM        │ l'image de départ (toujours  │ FROM php:8.3-apache        │
  │             │ en premier)                  │                            │
  ├─────────────┼──────────────────────────────┼────────────────────────────┤
  │ RUN         │ exécute une commande pendant │ RUN docker-php-ext-install │
  │             │  la construction de l'image  │  pdo_mysql                 │
  ├─────────────┼──────────────────────────────┼────────────────────────────┤
  │ COPY        │ copie des fichiers de ton PC │ COPY src/ /var/www/html/   │
  │             │  dans l'image                │                            │
  ├─────────────┼──────────────────────────────┼────────────────────────────┤
  │             │ définit le dossier courant   │                            │
  │ WORKDIR     │ pour les instructions        │ WORKDIR /var/www/html      │
  │             │ suivantes                    │                            │
  ├─────────────┼──────────────────────────────┼────────────────────────────┤
  │ ENV         │ définit une variable         │ ENV APP_ENV=prod           │
  │             │ d'environnement              │                            │
  ├─────────────┼──────────────────────────────┼────────────────────────────┤
  │             │ documente le port utilisé    │                            │
  │ EXPOSE      │ (n'ouvre rien : c'est -p qui │ EXPOSE 80                  │
  │             │  publie)                     │                            │
  ├─────────────┼──────────────────────────────┼────────────────────────────┤
  │ CMD         │ la commande lancée au        │ CMD ["apache2-foreground"] │
  │             │ démarrage du conteneur       │                            │
  └─────────────┴──────────────────────────────┴────────────────────────────┘

  ▎ Ne confonds pas RUN et CMD : RUN s'exécute une seule fois, à la construction
  ▎ de l'image, alors que CMD s'exécute à chaque démarrage d'un conteneur.

  ---

  2. Exercice A : construire ton image PHP

  On prépare le projet :

  mkdir -p ~/docker-cours/monapp/src
  cd ~/docker-cours/monapp

  Crée le fichier src/index.php :

  <?php
  echo "<h1>Mon application PHP dans Docker</h1>";
  echo "<p>Version de PHP : " . PHP_VERSION . "</p>";
  echo "<p>pdo_mysql installé : " . (extension_loaded('pdo_mysql') ? '✅ oui' :
  '❌ non') . "</p>";

  Crée le fichier Dockerfile, sans extension, à la racine de monapp/ :

  # 1. Point de départ : PHP 8.3 avec le serveur Apache déjà configuré
  FROM php:8.3-apache

  # 2. Installer l'extension MySQL pour PHP
  RUN docker-php-ext-install pdo_mysql

  # 3. Se placer dans le dossier web d'Apache
  WORKDIR /var/www/html

  # 4. Copier notre code dans l'image
  COPY src/ .

  # 5. Documenter le port utilisé par Apache
  EXPOSE 80

  # (Pas besoin de CMD : l'image php:8.3-apache démarre déjà Apache)

  Construis l'image :

  docker build -t monapp:1.0 .

  - -t monapp:1.0 donne à l'image le nom monapp et le tag (version) 1.0.
  - Le . final est le contexte de construction : le dossier dont Docker peut
    copier les fichiers. Ne l'oublie pas !

  Ensuite, lance un conteneur avec ton image :

  docker images                                   # monapp:1.0 apparaît dans la 
  liste
  docker run -d --name monapp -p 8090:80 monapp:1.0

  → http://localhost:8090 doit afficher PHP 8.3 et pdo_mysql : ✅ oui.

  3. Exercice B : comprendre le cache des couches

  Chaque instruction crée une couche (layer) dans l'image. Docker garde ces
  couches en cache pour ne pas tout refaire à chaque construction.

  Relance exactement la même construction :

  docker build -t monapp:1.0 .

  Elle prend environ une seconde, et tu vois CACHED sur chaque étape.

  Maintenant, modifie src/index.php (change le titre, par exemple) et
  reconstruis en version 1.1 :

  docker build -t monapp:1.1 .

  Observe la sortie : FROM et RUN sont CACHED, et seul COPY est refait. C'est
  pour ça que l'ordre compte :

  FROM          ← change rarement
  RUN install   ← change rarement     } mis en cache
  COPY code     ← change souvent      ← à mettre EN DERNIER

  Si tu mettais le COPY avant le RUN, chaque modification de ton code
  relancerait toute l'installation des extensions. Avec un vrai projet, ça peut
  prendre plusieurs minutes.

  Pour voir les couches d'une image :

  docker history monapp:1.1

  Important : ton conteneur monapp affiche toujours l'ancienne version. Une
  image est figée : pour voir la nouvelle version, il faut recréer le conteneur
  à partir de la nouvelle image.

  docker rm -f monapp
  docker run -d --name monapp -p 8090:80 monapp:1.1

  ---

  4. Le fichier .dockerignore

  C'est l'équivalent de .gitignore : les fichiers listés ne sont jamais envoyés
  à la construction. Crée le fichier .dockerignore à côté du Dockerfile :

  .git
  .env
  node_modules
  vendor
  *.log

  Il rend la construction plus rapide, et surtout il évite d'embarquer tes
  secrets (.env) dans une image que tu pourrais partager.

  ---

  5. Bind mount ou COPY ?

  ┌─────────────┬─────────────────────────────┬────────────────────────────┐
  │             │       Bind mount (-v)       │  COPY dans le Dockerfile   │
  ├─────────────┼─────────────────────────────┼────────────────────────────┤
  │ Quand       │ en développement            │ pour livrer (production)   │
  ├─────────────┼─────────────────────────────┼────────────────────────────┤
  │ Code        │ visible immédiatement       │ il faut reconstruire       │
  │ modifié     │                             │ l'image                    │
  ├─────────────┼─────────────────────────────┼────────────────────────────┤
  │ Autonome ?  │ non, il faut le dossier du  │ oui, l'image contient tout │
  │             │ PC                          │                            │
  └─────────────┴─────────────────────────────┴────────────────────────────┘

  En pratique, on utilise souvent les deux : COPY dans le Dockerfile, plus un
  bind mount en développement qui masque ce code par ta version en cours
  d'édition.

  ---

  Récap

  FROM → RUN → WORKDIR → COPY → EXPOSE → CMD     (du plus stable au plus 
  changeant)
  docker build -t nom:version .                  → construire
  docker history nom:version                     → voir les couches
  .dockerignore                                  → exclure des fichiers

● Leçon 6 : Docker Compose

  Avec Compose, toute l'application (PHP + MySQL, avec leurs ports, volumes et
  variables) tient dans un seul fichier, et se lance avec une seule commande.

  ---

  1. Le point clé : le réseau automatique

  Compose crée un réseau commun à tous les services. Chaque service est
  joignable par son nom :

  [navigateur] → localhost:8090 → [app : PHP/Apache] → db:3306 → [db : MySQL]
                                   └── réseau créé automatiquement par Compose 
  ──┘

  ▎ ⚠️ Piège classique : depuis le conteneur app, la base ne s'appelle pas 
  ▎ localhost, mais db. Dans un conteneur, localhost désigne le conteneur 
  ▎ lui-même.

  ---

  2. Préparation

  On libère les ports et les noms utilisés dans les leçons précédentes :

  docker rm -f monweb monapp madb
  cd ~/docker-cours/monapp

  Pas d'inquiétude : le volume mesdonnees n'est pas touché, docker rm ne
  supprime jamais un volume nommé.

  ---

  3. Exercice : l'appli complète

  a) Remplace src/index.php par un compteur de visites stocké dans MySQL :

  <?php
  $pdo = new PDO(
      'mysql:host=' . getenv('DB_HOST') . ';dbname=' . getenv('DB_NAME'),
      getenv('DB_USER'),
      getenv('DB_PASSWORD')
  );

  $pdo->exec("CREATE TABLE IF NOT EXISTS visites (id INT AUTO_INCREMENT PRIMARY 
  KEY, quand DATETIME)");
  $pdo->exec("INSERT INTO visites (quand) VALUES (NOW())");
  $total = $pdo->query("SELECT COUNT(*) FROM visites")->fetchColumn();

  echo "<h1>Mon appli PHP + MySQL avec Compose</h1>";
  echo "<p>Nombre de visites : <strong>$total</strong></p>";

  Les paramètres de connexion viennent des variables d'environnement, qu'on
  définit dans Compose.

  b) Crée compose.yaml à côté du Dockerfile :

  services:
    app:
      build: .                      # construit l'image depuis TON Dockerfile
      ports:
        - "8090:80"
      volumes:
        - ./src:/var/www/html       # bind mount : code modifiable en direct
      environment:
        DB_HOST: db                 # ← nom du service = adresse réseau
        DB_NAME: boulot
        DB_USER: appuser
        DB_PASSWORD: apppass
      depends_on:
        db:
          condition: service_healthy   # attend que MySQL soit VRAIMENT prêt

    db:
      image: mysql:8
      environment:
        MYSQL_ROOT_PASSWORD: secret
        MYSQL_DATABASE: boulot      # base créée automatiquement au 1er 
  démarrage
        MYSQL_USER: appuser
        MYSQL_PASSWORD: apppass
      volumes:
        - dbdata:/var/lib/mysql
      healthcheck:
        test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot",
  "-psecret"]
        interval: 5s
        retries: 10

  volumes:
    dbdata:

  Tu reconnais tout ce que tu as appris jusqu'ici :

  ┌──────────────┬──────────────────────────┐
  │  docker run  │       compose.yaml       │
  ├──────────────┼──────────────────────────┤
  │ --name       │ nom du service (app, db) │
  ├──────────────┼──────────────────────────┤
  │ -p 8090:80   │ ports:                   │
  ├──────────────┼──────────────────────────┤
  │ -v ...       │ volumes:                 │
  ├──────────────┼──────────────────────────┤
  │ -e VAR=val   │ environment:             │
  ├──────────────┼──────────────────────────┤
  │ docker build │ build: .                 │
  └──────────────┴──────────────────────────┘

  c) Lance tout :

  docker compose up -d
  docker compose ps        # attends que db soit "healthy" et app "running"

  → Ouvre http://localhost:8090 et rafraîchis plusieurs fois : le compteur
  augmente. 🎉

  ---

  4. Pourquoi healthcheck ?

  - depends_on seul garantit que db démarre avant app. Mais MySQL met environ 15
    secondes à être prêt, et PHP aurait planté avec « Connection refused ».
  - Avec condition: service_healthy, Compose attend que le test du healthcheck
    réussisse avant de lancer app.

  ---

  5. Les commandes du quotidien

  docker compose logs -f app          # logs d'un service
  docker compose exec db mysql -uappuser -papppass boulot -e "SELECT * FROM 
  visites;"
  docker compose stop                 # tout arrêter (rien n'est supprimé)
  docker compose start                # tout redémarrer
  docker compose up -d --build        # après une modification du Dockerfile
  docker compose down                 # supprime conteneurs + réseau, GARDE les 
  volumes
  docker compose down -v              # ⚠️ supprime AUSSI les volumes → données 
  perdues

  Test de persistance : fais docker compose down, puis docker compose up -d. Le
  compteur reprend où il en était, grâce au volume dbdata. En revanche, down -v
  le remettrait à zéro : c'est la commande à ne pas lancer en production !

  Test du bind mount : modifie le <h1> dans src/index.php et rafraîchis la page.
  C'est immédiat, sans reconstruction.

  ---

  6. Bonne pratique : les secrets dans .env

  Compose lit automatiquement un fichier .env placé à côté de compose.yaml :

  # .env
  DB_PASSWORD=apppass

        DB_PASSWORD: ${DB_PASSWORD}

  Ajoute .env dans .gitignore et dans .dockerignore : tes mots de passe ne
  finiront ni sur GitHub ni dans l'image.

  Les deux façons d'obtenir une image dans Compose

    db:
      image: mysql:8     # ← image TOUTE FAITE, téléchargée depuis Docker Hub

    app:
      build: .           # ← image CONSTRUITE à partir du Dockerfile du dossier

  le Dockerfile. Or ce Dockerfile, celui de la leçon 5, commence par :

  FROM php:8.3-apache

  Docker Hub : php:8.3-apache     (Debian + Apache + PHP 8.3, déjà configurés)
          │
          │  FROM  (on hérite de tout ça)
          ▼
  Ton Dockerfile : + RUN pdo_mysql + COPY src/
          │
          │  docker compose up  →  build automatique
          ▼
  Image « monapp-app »  ──►  conteneur app  ──►  Apache exécute index.php

  L'image officielle php:8.3-apache contient déjà Apache avec le module PHP 
  activé. Quand ton navigateur demande index.php, Apache le fait exécuter par
  PHP.

  tu avais fait la leçon 5) puis construit ton image.

  docker images                   # tu verras php:8.3-apache ET monapp-app
  docker compose exec app php -v  # PHP 8.3.x tourne bien dans le conteneur app
  docker history monapp-app       # les couches de php:8.3-apache, puis les 
  tiennes

  build: ..
